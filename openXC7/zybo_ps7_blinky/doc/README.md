# zybo_ps7_blinky

Demonstrates the Zybo Z7-20's ARM Cortex-A9 (the Zynq's "PS", not just the
FPGA fabric): a bare-metal ELF running on **CPU core 0** writes to a custom
AXI-Lite GPIO peripheral in the PL fabric over the PS7's `M_AXI_GP0` bus to
blink the LEDs, instead of the LEDs being driven directly by fabric logic.

This is intentionally **single-core**: Zynq boots CPU0 only, and CPU1 stays
asleep (WFE) unless explicitly woken with its own entry-point/SEV code,
which this example does not do. Treat that as a follow-up, not included
here.

## Hardware

| | |
|---|---|
| Board  | Digilent Zybo Z7-20 |
| FPGA   | Zynq-7020 `xc7z020clg400-1` |
| Clock  | `clk` -> pin K17, 125 MHz onboard oscillator |
| LEDs   | `led[0..3]` -> M14, M15, G14, D18 |
| Switches | `sw[0..3]` -> G15, P15, W13, T16 (wired to the AXI-GPIO peripheral's input register; not read by the current software, but readable) |

## Layout

- `hdl/`, `xdc/` - PL fabric source and pin constraints, as usual
- `sw/` - actually used here: `build.sh` builds the ARM-side FSBL/app and
  packages `BOOT.BIN` (clones `embeddedsw`/`zynq-mkbootimage` here on
  first run)
- `tools/zybo_z7_20_bsp/` - the hand-assembled board-support files
  (`ps7_init.c` etc.) copied into the FSBL build; also holds the cached
  chip database like the other examples
- `tools/qspi_flash_writer/` - only used by the optional
  `make qspi-flash-writer` (see below)
- `tools/openocd_zybo_z7_20.cfg`, `tools/gen_ps7_init_tcl.py`,
  `tools/jtag_run.sh` - only used by the optional `make jtag-run`
  (see below); `ps7_init_jtag.tcl` is regenerated fresh each run, not
  meant to be hand-edited
- `sim/` - intentionally empty: simulating PS7 boot/AXI behavior needs
  Xilinx's proprietary simulation models, which aren't available here
- `build/` - generated bitstream + `BOOT.BIN`; safe to delete (`make clean`)

## How it works

- `hdl/ps7_axi_blinky.v` instantiates the raw `PS7` primitive plus a small
  hand-written AXI-Lite GPIO slave (`axil_gpio`) wired to `M_AXI_GP0`.
  `led[3:0]` is driven directly by the peripheral's output register --
  whatever CPU0 writes there shows up on the LEDs.
- `tools/zybo_z7_20_bsp/ps7_init.c` is the PS7 clock/DDR/MIO init table
  the FSBL runs before anything else. It was **not** generated by GenZ
  (GenZ has no Zybo Z7-20 preset, and hand-deriving one is error-prone).
  Instead it's assembled from Xilinx's own Vivado-generated register data
  for this exact board, sourced from u-boot's
  `board/xilinx/zynq/zynq-zybo-z7/ps7_init_gpl.c` (whose own header
  comment documents it was generated from the official "Zybo-z7-20
  board" Vivado preset), spliced into the FSBL's `zc702` BSP template
  (same Zynq-7020 silicon, so everything except the actual PLL/clock/DDR/
  MIO/peripherals tables is identical boilerplate).
- `sw/build.sh` builds the FSBL and a `hello-world.elf` (built with
  `-DAXI_TEST`, from the openXC7 `embeddedsw` fork) that writes an
  alternating `0x5`/`0xa` pattern to the AXI-GPIO peripheral once per
  second, and packages both plus the bitstream into `build/BOOT.BIN`.
- Boot is **NODDR** (no DDR init/use) -- this demo doesn't need DRAM, and
  skipping it removes an entire class of board-specific calibration risk.

## One-time environment setup

```bash
source ~/oss-cad-suite/environment   # yosys, openFPGALoader (not used for boot, but handy)
source /opt/openxc7/export.sh        # nextpnr-xilinx, prjxray tools
```

`sw/build.sh` additionally downloads its own `arm-none-eabi-gcc` toolchain
on first run (~150MB) -- do **not** use the distro's `gcc-arm-none-eabi`
package, it's known to be incompatible with this BSP build.

## Usage

```bash
make bitstream   # synthesize + place&route -> build/ps7_axi_blinky.bit
make software    # build FSBL + app, package -> build/BOOT.BIN (needs bitstream first)
make all         # both
make clean       # remove build/ (keeps tools/chipdb and sw/'s cloned repos)
```

## Booting it

1. Copy `build/BOOT.BIN` to a FAT32-formatted microSD card.
2. Insert the card into the Zybo Z7-20's `J4` slot.
3. Set the `JP5` boot-mode jumper to **SD** (it defaults to JTAG).
4. Power-cycle the board.

Expect LEDs 0/2 and 1/3 to alternate once per second, forever. If you have
a serial terminal on the board's USB-UART port (115200 8N1), you should
also see "Hello World" followed by repeated "Hello" lines.

## Booting from QSPI instead of SD

The Zybo Z7-20 has onboard QSPI flash (16MB) and a JP5 "QSPI" boot-mode
setting, but it's PS-side-only memory -- `openFPGALoader` (JTAG-based)
cannot write it, only code running on the ARM core can. `make
qspi-flash-writer` builds a one-time provisioning image for exactly that:

```bash
make qspi-flash-writer   # needs `make software` run first
```

This produces `build/qspi_flash_writer.BOOT.BIN`, a separate minimal
image (the same NODDR `fsbl.elf` as the main demo, plus a small ARM
program using the `XQspiPs`/`XilFFs` drivers) that reads a file called
`TARGET.BIN` from the SD card and writes it into QSPI flash page by
page, verifying each one immediately by reading it back.

To provision the board:

1. On a FAT32 SD card, place **both**:
   - `build/qspi_flash_writer.BOOT.BIN` -> copied to the card **as `BOOT.BIN`**
   - `build/BOOT.BIN` (the real system image) -> copied to the card **as `TARGET.BIN`**
2. Boot as usual (JP5 -> SD). Watch the serial console (115200 8N1) --
   it prints progress and a final `DONE` (or a clear error) message.
3. Once you see `DONE`, power off, set JP5 to **QSPI**, and power back on.
   The board now boots standalone; the SD card is no longer needed.

This flash-writer links the SD and QSPI drivers simultaneously, which
barely fits the ~63.5KB on-chip RAM (`ps7_ram_1`) the other apps here
also use -- it took FatFs read-only/no-LFN trimming, a much smaller
stack/heap, and fixing two places where `-ffunction-sections` wasn't
actually reaching the compiler (see the comments in
`tools/qspi_flash_writer/lscript.ld`, `xparameters.h`, and
`sw/build-qspi-flash-writer.sh` for the details). An earlier version of
this ran from DDR instead, with its own DDR-initializing FSBL, to avoid
that squeeze -- it hung completely on real hardware during DDR
calibration with zero UART output. Bare-metal DDR bring-up without a
JTAG debugger is too risky to chase blind, so this stays OCM-only.

## Fast iteration: JTAG debug-run (no SD card, no FSBL, no BOOT.BIN)

For rapid development, `make jtag-run` skips the whole boot chain:
it halts CPU0 over JTAG, hand-runs the PS7 clock/MIO/peripherals init
(the exact same authoritative register data the FSBL uses, translated
to Tcl by `tools/gen_ps7_init_tcl.py` so it can never drift out of sync
with it), loads the bitstream via `openFPGALoader`, enables the PS-PL
level shifters, loads an ELF straight into memory, and jumps to it.
Round-trip is a few seconds instead of a full SD card copy-and-boot.

**Set JP5 to JTAG** (not SD/QSPI) for this, and **open your serial
terminal (115200 8N1) before running it**: the app's first prints fire
the instant the core resumes, and bytes already sent over UART can't be
replayed if you connect late.

```bash
make jtag-run                              # defaults to hello-world.elf (AXI_TEST)
tools/jtag_run.sh path/to/other.elf         # or run a different ELF directly
```

This only runs CPU0 (matching the rest of this project -- CPU1 stays
asleep) and doesn't touch DDR, so it only works for plain OCM-resident
apps like the ones here, not anything requiring DRAM.

If OpenOCD's raw USB access leaves your serial port device gone
afterward (it can detach the kernel driver from the whole FTDI chip, not
just the JTAG half), replug the USB cable, or rebind it without
power-cycling the board:
```bash
echo <bus>-<port>:1.1 | sudo tee /sys/bus/usb/drivers/ftdi_sio/bind
```
(find `<bus>-<port>` via `ls /sys/bus/usb/devices/ | grep <your bus>`;
`:1.1` is the second interface, normally the UART one). Note that which
device node (`/dev/ttyUSB0` vs `/dev/ttyUSB1`) ends up being the UART
isn't fixed -- it depends on binding order/history, not just which FTDI
interface it is -- so if one doesn't show output, try the other.
